ABSTRACT
Sahaiy is an enterprise-oriented AI call agent platform that combines a multi-page web dashboard (Vite + Vanilla JavaScript) with a FastAPI backend for real-time voice interactions. The product supports agent creation, authentication, conversation logging, analytics, phone number management, knowledge document management, and a playground for testing live AI voice calls. The backend pipeline integrates STT, LLM, and TTS services and exposes both REST endpoints and WebSocket streaming. Supabase is used as the primary data and auth platform, with RLS policies for tenant-safe client access, while server-side service-role operations support backend workflows. The codebase indicates a practical MVP-to-production architecture with strong modular separation (services, components, routers) and support for future expansion such as LiveKit WebRTC and richer RAG ingestion.


CHAPTER 1: INTRODUCTION

1.1 Background of the Study
Modern customer operations require high-volume, low-latency, multilingual call handling. Human-only call centers face cost, scalability, availability, and consistency constraints, especially for repetitive tasks (order status, FAQs, lead qualification, appointment workflows). Sahaiy addresses this by combining real-time speech transcription, language model reasoning, and speech synthesis in an integrated call-agent platform. The system targets Hindi/English and Indian-market usage patterns and provides business observability through conversation and daily statistics tracking.

1.2 Objectives
The implemented codebase reflects the following product objectives:
1) Provide no-code/low-code AI agent setup (name, template, prompt, first message, voice, language).
2) Support secure user onboarding via Supabase Auth (email/password and OAuth providers).
3) Store and manage call conversations, messages, phone numbers, tools, and knowledge assets per user.
4) Offer real-time call test capability through a WebSocket-based playground.
5) Enable retrieval-assisted responses through optional FAISS + sentence-transformers RAG.
6) Present analytics and operational dashboards for calls, status distribution, and trends.
7) Maintain modular architecture where UI, data services, and backend AI pipeline are separated.

1.3 Scope and Limitations
Scope:
- Frontend includes landing page, auth page, and dashboard modules for agents, knowledge, tools, integrations, voices, conversations, analytics, phone numbers, tests, and settings.
- Backend includes health, STT forwarding, call lifecycle APIs, knowledge ingestion APIs, phone number APIs, LiveKit token API, and main WebSocket voice pipeline.
- Database schema covers profiles, agents, conversations, conversation messages, phone numbers, knowledge docs, tools, and daily stats.

Limitations observed in current implementation:
- RAG retrieval currently indexes provided text in memory; persistent vector storage lifecycle is limited.
- Some dashboard sections are UI-ready but rely on future deeper backend integrations (for example advanced outbound/WhatsApp workflows).
- Voice pipeline quality and latency depend on external STT/LLM/TTS service availability and model hosting.
- Hardware requirements are environment-dependent and not formally benchmarked in code-level documentation.

Organizations handling customer communication need a scalable way to automate voice calls without sacrificing conversational quality and context-awareness. Existing manual processes create delays, high operational costs, inconsistent service quality, and limited after-hours support.

CHAPTER 3: DATA ENGINEERING APPROACH

3.1 Software Model used
The implemented architecture follows a layered service-oriented model with event-driven real-time paths:
- Presentation Layer: HTML + Vanilla JS pages and reusable UI components.
- Frontend Data Service Layer: Dedicated service modules for auth, agents, conversations, analytics, and realtime subscriptions.
- API Layer: FastAPI routers segmented by domain (STT, calls, audio websocket, knowledge, phone numbers, health, livekit).
- AI Processing Layer: STT forwarding, LLM prompt streaming, TTS conversion, VAD interruption logic.
- Data Layer: Supabase PostgreSQL + Auth + Realtime, with RLS and indexed tables.

Data flow model:
User Audio -> WebSocket (/ws/audio) -> STT -> Prompt Builder (+ optional RAG context) -> LLM stream -> TTS -> Audio frames back to client

3.4 Platform Specification

4.1 Use Case Diagram

Main use cases (derived from code routes/UI modules):

4) Start and test voice call via playground.
5) Store and view conversations/transcripts.
6) Add and map knowledge documents.
7) Manage phone numbers and tools.
8) View analytics and recent call activity.

4.2 Sequence Diagram
Representative sequence for playground live call:
1) User opens playground and selects agent.
2) Browser requests microphone and opens WS connection (/ws/audio?agent_id&user_id).
3) Backend optionally sends first_message as text fragment + synthesized audio.
4) Browser streams audio chunks.
5) Backend batches audio and calls STT service.
6) Transcript is sent back to client as JSON control frame.
7) Backend builds prompt (+ optional retrieved context) and streams LLM fragments.
8) For each fragment, backend calls TTS and sends WAV bytes to client.
9) Client plays audio incrementally and displays transcript fragments.
10) If interruption detected (client signal or VAD), backend cancels in-flight generation/audio.

4.3 Activity Diagram
Operational activity flow:
- Authenticate user -> Load profile -> Seed default data (if new user) -> Fetch agents/conversations/docs/tools/stats -> Render dashboard.
- On navigation, render module-specific UI (agents/conversations/analytics/knowledge/phones).
- In background, subscribe to realtime inserts/updates for conversations and agents.
- Periodic ticker simulates call events for dashboard liveliness.
- User actions (create agent, delete phone number, upload doc) trigger service-layer calls and UI refresh.


CHAPTER 5: IMPLEMENTATION PHASE

5.1 Technology Used & its Characteristics
A) Frontend
- Vite MPA: Fast dev server, optimized production bundle, separate entry points for landing/auth/dashboard.
- Vanilla JS module architecture: Lightweight, explicit import boundaries, easier direct control.
- Service-layer pattern: Keeps Supabase/API logic out of components for maintainability.
- Realtime subscriptions: Supabase postgres_changes channels for live dashboard updates.

B) Backend
- FastAPI asynchronous stack: Suitable for concurrent IO-heavy speech/LLM/TTS orchestration.
- Router modularity: Each domain endpoint isolated for cleaner scaling and testing.
- Shared httpx client lifecycle: Connection pooling and reduced overhead.
- WebSocket full-duplex pipeline: Real-time bi-directional audio/text communication.

C) Data & Security
- Supabase Auth + profiles auto-provisioning via trigger.
- RLS policies for user-scoped CRUD on all key tables.
- Indexed query patterns for agents, conversations, docs, and messages.
- Service-role backend client kept server-side only.

D) AI stack
- STT via whisper server endpoint.
- LLM via llama server streaming completion endpoint.
- TTS via Sarvam API with speaker mapping.
- VAD via RMS-energy threshold for interruption control.

CHAPTER 6: RESULTS AND DISCUSSION

6.1 Results
From code-level evidence, the implemented solution achieves:
1) End-to-end voice test loop (audio input to AI response audio output) through WebSocket pipeline.
2) Multi-module dashboard with user authentication and per-user data segregation.
3) Working CRUD foundation for agents, conversations, phone numbers, and knowledge docs.
4) Realtime updates for key entities (agents/conversations).
5) Seeded onboarding for new users (demo agents, conv logs, docs, stats) enabling immediate product walkthrough.
6) Extensible architecture for future telephony and WebRTC integration.

6.2 Discussion
Strengths:
- Clean separation of concerns across frontend services/components and backend routers/services.
- Practical database modeling with RLS and indexes.
- Strong base for low-latency conversational experience using streaming fragments and incremental TTS.

Trade-offs / Current gaps:
- Production-grade telephony lifecycle is still evolving beyond playground and base APIs.
- RAG currently relies on in-memory indexing, which can constrain persistence and scale.
- Some UI sections indicate roadmap-level capability beyond current fully wired backend behavior.
- Real-world latency/SLA depends heavily on external model servers and network conditions.


CHAPTER 7: CONCLUSIONS & FUTURE WORK

Conclusion
The Sahaiy codebase demonstrates a robust AI call-agent platform foundation with operational dashboarding, secure multi-tenant data access, and a functioning real-time voice interaction core. The current implementation is suitable for MVP-to-early production experimentation and provides strong structural patterns for incremental hardening.

Future Work

4) Advanced analytics dashboards with cohort, agent-level conversion, and SLA metrics.
5) Automated testing suite for WebSocket audio protocol and regression coverage.
6) Role-based workspace controls and enterprise administration modules.
7) Performance benchmarking and autoscaling strategy for STT/LLM/TTS services.
